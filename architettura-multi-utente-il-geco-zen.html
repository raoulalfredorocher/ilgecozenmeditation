Il Geco Zen — Architettura multi-utente

Piano tecnico per produzione: autenticazione, DB e sincronizzazione dati per centinaia di utenti

1 · Situazione attuale

L'app è una PWA pura (HTML/CSS/JS). I dati (template, cronologia) sono salvati nel localStorage del singolo browser/device. È installabile su iPhone via Safari "Aggiungi a schermata Home" grazie al manifest.json.

Cosa vive già nel localStorage
  • zen_v4 — array di preset/template personalizzati
  • zen_history — array di sessioni completate (timestamp + minuti + steps)
Problema multi-utente: localStorage è locale al singolo browser. Se l'utente reinstalla l'app, cambia device, o usa un secondo iPhone, perde tutto. Non c'è nessuna separazione tra utenti.

2 · Serve un DB? Serve l'autenticazione?

Dipende da quanto vuoi isolare i dati:

Approccio Autenticazione DB remoto Dati su altro device Costo Complessità
A · Solo localStorage (stato attuale) No No ❌ No Gratis Nulla
B · localStorage + export/import JSON No No ⚠️ Manuale Gratis Bassa
C · Firebase Auth + Firestore Raccomandato Google/Apple/Email Firestore (NoSQL) ✅ Automatico Gratis fino ~50k utenti Media

3 · Raccomandazione — Opzione C: Firebase

Firebase è la scelta ideale per questa app perché:

  • L'app resta statica su GitHub Pages — nessun server da gestire
  • Firebase Auth supporta "Accedi con Google" e "Accedi con Apple" — nessuna password da ricordare, perfetto per iPhone
  • Piano gratuito Spark: 50.000 auth/mese, 1 GiB Firestore, 10 GiB transfer — abbondante per centinaia di utenti meditatori
  • Firestore è offline-first: i dati si sincronizzano automaticamente anche senza rete, esattamente come un timer deve funzionare
  • SDK già integrato via CDN — zero backend da scrivere

4 · Schema Firestore proposto

users/{uid}
PK uid string
displayName string
createdAt timestamp
settings map (futura)
users/{uid}/presets/{id}
PK id auto-id
name string
steps array[{mins,name}]
order number
updatedAt timestamp
users/{uid}/sessions/{id}
PK id auto-id
ts timestamp
totalMins number
steps array[{mins,name}]
Subcollection per utente: ogni utente ha la propria subcollection presets e sessions. Non esiste modo per un utente di leggere i dati di un altro. Le Security Rules di Firestore lo impongono a livello server.

6 · Piano di implementazione (4 fasi)

Fase 1
~1h
Setup Firebase Prerequisito
Creare progetto Firebase, abilitare Auth (Google + Apple), creare database Firestore in modalità produzione, configurare Security Rules, aggiungere il dominio GitHub Pages ai domini autorizzati.
Fase 2
~2h
Autenticazione nell'app Codice
Aggiungere js/auth.js: banner login, pulsante "Accedi con Google", listener onAuthStateChanged, UI con avatar utente e logout. Nessuna modifica ai moduli esistenti in questa fase.
Fase 3
~2h
Sincronizzazione preset Codice
Modificare js/presets.js: loadPresets() e savePresets() leggono/scrivono da Firestore quando l'utente è loggato, altrimenti fallback a localStorage (utente anonimo). Migrazione automatica dei preset locali al primo login.
Fase 4
~2h
Sincronizzazione cronologia Codice
Modificare js/history.js: saveSession() scrive su Firestore, loadHistory() legge da Firestore. Il calendario funziona identicamente — solo i dati cambiano sorgente. Migrazione automatica delle sessioni locali.

7 · Security Rules Firestore (minimo necessario)

// Solo l'utente autenticato può leggere/scrivere i propri dati rules_version = '2'; service cloud.firestore { match /databases/{database}/documents { match /users/{userId}/{document=**} { allow read, write: if request.auth != null && request.auth.uid == userId; } } }

8 · Cosa rimane invariato

  • GitHub Pages come hosting — nessun server, nessun costo aggiuntivo
  • Il timer, i suoni, la UI, il CSS — nessuna modifica
  • L'app funziona offline — Firestore ha cache locale nativa
  • L'installazione PWA su iPhone rimane identica
  • Gli utenti che non vogliono fare login continuano a usare localStorage

9 · Quando scegliere Supabase invece di Firebase

Supabase (PostgreSQL) è preferibile solo se:

  • Hai già esperienza con SQL e vuoi query relazionali complesse
  • Vuoi un pannello admin con tabelle visuali (Supabase Studio è ottimo)
  • Devi esportare dati in formato SQL/CSV per analytics avanzate

Per questa app, Firestore batte Supabase su: semplicità di setup, supporto offline nativo, SDK mobile-first, e zero configurazione server.
